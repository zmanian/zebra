# Peer Cache Startup Ingest Hardening Note

Date: 2026-05-03

Last updated: 2026-05-09

Scope: startup peer-cache ingestion and initial peer admission in
`zebra-network`.

## Summary

`Config::load_peer_cache()` treats the peer-cache file as unbounded local input:
it reads the whole file into memory, parses every line, and logs invalid entries
one by one before later startup peer limits apply.

This is not a remote private-disclosure issue on current evidence. Zebra's own
cache writer caps persisted peer addresses at 75 entries, and startup connection
attempts are later capped and rate-limited. The risk is local or persisted-input
hardening: an oversized or malformed cache file can amplify startup memory, CPU,
log volume, and address-book update work before the normal dial caps take over.

## Evidence

Startup reads DNS peers and disk cache peers, then unions both sets:

- `zebra-network/src/config.rs:257-275`

Disk cache loading currently:

- calls `fs::read_to_string(&peer_cache_file).await`,
- iterates `peer_list.lines()`,
- parses every line as `PeerSocketAddr`,
- logs every invalid line individually,
- collects all valid entries into a `HashSet`.

Evidence:

- `zebra-network/src/config.rs:410-459`

The later startup admission path does cap live connection fanout, but only after
the cache has already been read and parsed:

- `zebra-network/src/peer_set/initialize.rs:475-540` builds the full initial
  peer preference map and sends every valid peer to the address-book updater
  before selecting the limited dial set.
- `zebra-network/src/peer_set/initialize.rs:361-390` staggers startup outbound
  attempts by `MIN_OUTBOUND_PEER_CONNECTION_INTERVAL`.
- `zebra-network/src/peer_set/initialize/tests/vectors.rs:1092-1135` covers the
  initial-peer rate limit.

Existing remote-path bounds:

- Zebra's peer-cache writer takes at most `MAX_PEER_DISK_CACHE_SIZE = 75`
  entries before writing: `zebra-network/src/constants.rs:183` and
  `zebra-network/src/config.rs:486-518`.
- The default startup dial target is 25:
  `zebra-network/src/constants.rs:85-86` and
  `zebra-network/src/config.rs:584`.
- `AddressBook::update()` enforces the address-book size cap by removing
  surplus entries: `zebra-network/src/address_book.rs:510-545`.

## Impact

An attacker who only talks to Zebra over the network should not be able to make
Zebra write an oversized peer-cache file through the reviewed path, because the
write side is capped.

The issue matters if the cache file is locally tampered with, restored from a
bad backup, generated by another process, or left behind by some separate bug.
On restart, Zebra can spend avoidable work on a file that is far larger than
anything Zebra would write itself.

## Classification

Public/local startup hardening. Not private disclosure. Local-only record, not
posted publicly.

## Local Proof

A focused current-behavior test was added:

```sh
cargo test -p zebra-network oversized_peer_cache_file_loads_more_than_writer_limit_today --lib
```

Result on 2026-05-09: passed. The test writes a temporary peer-cache file with
`MAX_PEER_DISK_CACHE_SIZE + 25` valid entries and confirms
`Config::load_peer_cache()` loads every entry today, rather than applying the
writer-side peer-cache limit to the read path.

The invalid-line logging and startup address-book update work remain
source-evidence-only, but the oversized valid-entry ingest is now covered by a
durable local proof.

## Suggested Fix

Treat the peer-cache file as bounded, untrusted local input:

- bound the bytes read before parsing,
- bound the number of cache lines accepted to `MAX_PEER_DISK_CACHE_SIZE`,
- optionally bound per-line length to a conservative `PeerSocketAddr` textual
  size,
- replace per-invalid-line logs with one aggregate warning,
- treat oversized cache files as soft cache misses and continue with DNS seed
  peers.

Regression tests should cover:

- oversized cache file is ignored,
- within-bound malformed cache logs once and loads valid entries,
- normal Zebra-written cache still loads.

## Confidence

High on the code shape and bounds. Low severity because the unbounded input is
local/persisted, while the normal remote-influenced write path is capped.
